# Methodology — Comparative Analysis of Logistic Regression and XGBoost for Cognitive Load Detection Using Eye-Tracking Features

Reference document for Chapter 3. Every decision below is implemented in `src/` and
every number quoted in Chapter 4 is regenerated by `python src/run_experiment.py`.

---

## 1. Research design

Quantitative, experimental, computational. Two supervised classifiers — Logistic
Regression as an interpretable linear baseline and XGBoost as a gradient-boosted
ensemble — are trained on identical inputs, evaluated under an identical protocol,
and compared on classification performance and feature attribution.

Scope note: the study uses the GAZELOAD dataset only. Cross-dataset generalisation
is not evaluated, and the corresponding objective has been withdrawn.

## 2. Dataset

GAZELOAD (Karbouj, Gaaloul & Krüger, 2025), a multimodal eye-tracking dataset
recorded during industrial human–robot collaboration with Meta Aria smart glasses.

| Property | Value |
|---|---|
| Participants | 26 |
| Tasks per participant | 5 |
| Recordings | 130 (complete 26 × 5 grid, no missing cells) |
| Published sampling unit | non-overlapping 250 ms windows |
| Windows total | 135,499 |
| Recordings with timing discontinuities | 0 |
| Label | `selfreport_mental_load(1-10)`, one value per recording |

### 2.1 Available features

The released `04_eye-metrics` files provide, per 250 ms window: fixation count,
saccade count, saccade amplitude, saccade velocity, gaze direction (x, y, z) with
per-window standard deviations, gaze position in the scene camera, gaze transition
entropy (GTE), fixation dispersion index (FDI), saccade rate, a binary blink flag,
and interpolated illuminance in lux.

### 2.2 Features that are not available

**Pupil diameter and pupil dilation are absent from the released dataset.** The
authors' `01_Metadata/pupil.py` derives them from raw `.vrs` Aria recordings, which
are not part of the public release. Any reference to pupil-based features must
therefore be removed from the study, and their absence stated as a limitation:
pupillometry is the single most established physiological correlate of cognitive
load in the literature, and this study cannot use it.

## 3. Data preparation

### 3.1 Participant identity

Participant identity is taken from the **filename**, not from the `Participant_ID`
column. That column contains the strings `Hedi` (recordings 01_2 to 01_4) and
`Wassim` (recordings 02_3 to 02_5) instead of numeric identifiers. Filenames are
internally consistent with the `tasks` column across all 130 recordings.

### 3.2 Columns excluded from the feature matrix

| Column | Reason for exclusion |
|---|---|
| `tasks` | Task index alone predicts the label at ROC-AUC 0.93. Retaining it would let both classifiers read the experimental condition rather than the participant's eyes. |
| `Participant_ID` | A grouping key, not a feature; also corrupted in six recordings. |
| `timestamps_start_ms`, `timestamps_end_ms` | Used to construct epochs, then discarded. Absolute recording time is not a workload feature. |

### 3.3 Temporal aggregation

The published 250 ms window is too short to carry the constructs this study
measures. Two of the supplied features are effectively constant at that resolution:
GTE is exactly zero in 98.8 % of windows, and the blink flag fires in 0.43 %.
A quarter of a second contains too few oculomotor events for a rate or an entropy
to be defined.

Windows are therefore aggregated into **30-second epochs**. Epoch boundaries are
computed from elapsed time within each recording, not from row position, so an epoch
can never span a recording boundary or a dropout. Epochs covering less than 80 % of
their nominal duration are discarded, which removes partial trailing epochs.

This yields **1,087 epochs**.

Per epoch, each of the sixteen base features contributes its mean and standard
deviation. Five further features are derived:

| Derived feature | Definition and rationale |
|---|---|
| `blink_rate` | Proportion of windows in the epoch containing a blink. This is the "blink rate" the literature refers to; the raw per-window flag is not. |
| `gte_nonzero_frac` | Proportion of windows with non-zero gaze transition entropy — the usable form of GTE at epoch scale. |
| `sacc_missing_frac` | Proportion of windows with no saccade. |
| `fdi_missing_frac` | Proportion of windows with fewer than two fixations. |
| `fixation_zero_frac` | Proportion of windows with no fixation. |

Total: **37 features**.

### 3.4 Missing values are structural

Missingness in this dataset is not random and must not be treated as noise:

- `saccade_amplitude_degree` and `saccade_velocity_degree/s` are missing in exactly
  those windows where `saccade_count == 0` (23.9 % of windows).
- `FDI` is missing in exactly those windows where `fixation_count < 2` (11.7 %).

A window with no saccade is a measurement, not a gap. The proportion of such windows
within an epoch is therefore retained as a feature (§3.3), and the two classifiers
handle the remaining missing values according to what each can represent:

- **XGBoost** receives the missing values untouched and learns a default branch
  direction for them.
- **Logistic Regression** cannot represent a missing value, so it receives a median
  imputation **plus a binary indicator per affected column**, preserving the
  information a plain fill would erase.

## 4. Target variable

The label is the participant's own workload rating on a 1–10 scale, recorded once per
recording. It is converted to a binary high/low target. Two conversions are
evaluated; both use only the rating.

### 4.1 Absolute threshold (primary)

A rating of **4 or above** is high load. This applies one boundary to every
participant and retains all 1,087 epochs.

### 4.2 Within-participant threshold (comparison)

A rating **above that participant's own median rating** is high load. Ratings at a
participant's median are ambiguous — neither more nor less demanding than their
typical task — and are excluded rather than forced into a class, leaving 768 epochs.

The motivation is that participants do not share a scale. In this dataset P12 never
rated a task above 3 and P15 never rated one below 6. Under an absolute threshold,
every P12 recording is low and every P15 recording is high, so a classifier can score
well by recognising the participant rather than the workload — and a single 250 ms
window identifies which of the 26 participants produced it at 24.3 % accuracy against
a 3.8 % chance baseline.

### 4.3 Validating the within-participant threshold

Re-cutting each participant at their own median risks manufacturing a contrast for a
participant whose tasks were uniformly easy. Two checks address this:

1. **Rating spread per participant** is reported. Only one participant of 26 (P12)
   has a rating range below three points.
2. **Agreement with objective task difficulty.** Task difficulty is fixed by the
   experimental protocol, so labels that capture real workload should concentrate on
   the later tasks. They do: the correlation between task index and the
   within-participant label is Spearman ρ = 0.735 (p < .001), against ρ = 0.534
   for the absolute threshold.

## 5. Feature scaling

Two schemes are evaluated:

- **Raw.** Values as aggregated.
- **Per-participant standardisation.** Each feature is re-expressed as a deviation
  from that participant's own mean in units of their own standard deviation, so a
  value of +2 means "two SDs above what this person normally shows."

The transform for any participant is computed exclusively from that participant's own
feature values and uses no labels, so no information crosses between participants and
the protocol in §6 is not compromised. It does, however, imply that a deployed system
would require a short calibration recording from each new user. That is a genuine
deployment constraint and belongs in the limitations.

## 6. Evaluation protocol

### 6.1 Why not a random split

The label is constant within each recording, so the 135,499 windows carry only **130
independent label observations.** A random split over epochs places recordings from
the same participant on both sides of the split, and the resulting score measures
participant recognition as much as workload detection. Measured on this dataset, a
random split inflates ROC-AUC by approximately 0.10.

### 6.2 Leave-one-participant-out

**Outer loop:** 26 folds. Each fold trains on 25 participants and tests on the single
held-out participant, so no participant contributes to both training and testing.
Grouping at participant level rather than recording level also absorbs the temporal
autocorrelation between adjacent epochs, since all of a participant's epochs fall on
the same side of every split.

**Inner loop:** hyperparameters are selected within each outer fold using 5-fold
stratified group cross-validation over the 25 training participants only. The
held-out participant is never used for tuning, so the reported scores are not
inflated by hyperparameter selection.

| Model | Tuned over |
|---|---|
| Logistic Regression | `C` ∈ {0.01, 0.1, 1, 10} |
| XGBoost | `max_depth` ∈ {2, 3, 4}, `learning_rate` ∈ {0.05, 0.1}, `n_estimators` ∈ {200, 400} |

A final holdout partition is deliberately **not** reserved. With 26 participants,
withholding six would leave twenty for training and produce a test estimate too
unstable to interpret.

### 6.3 Metrics

Accuracy, precision, recall, F1-score and ROC-AUC, reported two ways:

- **Pooled** — held-out predictions from all 26 folds concatenated and scored once.
  This is the headline, and it avoids the problem that a participant whose recordings
  all fall in one class has no defined ROC-AUC of their own.
- **Per-participant** — 26 separate scores summarised as mean ± SD, showing the
  between-person variability that pooling hides. ROC-AUC is reported only for
  participants with both classes present.

Balanced accuracy is reported alongside accuracy because the classes are not exactly
even.

### 6.4 Reference points

Every results table is accompanied by two reference values, so a reader can judge
whether a score is meaningful rather than merely non-zero:

- **Majority-class baseline** — accuracy from always predicting the training-set
  majority class, computed under the same LOPO protocol.
- **Task-index ceiling** — ROC-AUC obtained from the task number alone. Because the
  self-report largely restates objective task difficulty, this quantifies how much of
  the target any gaze-based model could in principle recover.

### 6.5 Comparing the two models

A difference in pooled ROC-AUC is a single number with no uncertainty attached. The
claim that one model outperforms the other is therefore tested with a **paired
Wilcoxon signed-rank test** over the per-participant scores of the 26 held-out folds.

## 7. Experimental configurations

Eight configurations cross the two labellings, two feature schemes, and
illuminance inclusion/exclusion. Illuminance is an environmental variable rather
than an oculomotor one, and lighting differs between tasks, so removing it tests
how much of any result is ambient light rather than eye behaviour.

| Config | Label | Features | Illuminance |
|---|---|---|---|
| A (headline) | absolute, ≥ 4 | raw | included |
| B | absolute, ≥ 4 | raw | removed |
| C | absolute, ≥ 4 | per-participant | included |
| C_no_lux | absolute, ≥ 4 | per-participant | removed |
| D | within-participant | raw | included |
| D_no_lux | within-participant | raw | removed |
| E | within-participant | per-participant | included |
| F | within-participant | per-participant | removed |

## 8. Feature importance

Importance is extracted from the same fold models that produced the reported scores,
not from a separate model refitted on all data, so the explanation and the performance
claim describe the same object.

| Model | Method |
|---|---|
| Logistic Regression | Mean standardised coefficient across the 26 folds, with its standard deviation and the proportion of folds sharing its sign. Features are standardised inside the pipeline, so coefficients are mutually comparable and their sign is interpretable. |
| XGBoost | Mean gain importance across folds, plus **out-of-fold SHAP values** — each fold's model explains only the participant it never trained on. |

Reporting the across-fold standard deviation matters: a feature that dominates in
three folds and vanishes in the remaining twenty-three is not a finding.

## 10. Limitations arising from the method

1. Pupil diameter and dilation, the most established physiological indices of
   cognitive load, are unavailable in the released dataset.
2. The target is self-reported workload, not an objective measure, and it is recorded
   once per recording rather than continuously — so within-recording variation in
   actual load is unobservable.
3. With 130 independent label observations from 26 participants, confidence intervals
   on any performance estimate are wide.
4. Per-participant standardisation, where used, implies a per-user calibration
   recording in any deployed system.
5. Illuminance covaries with task, so results that depend on it cannot be attributed
   to oculomotor behaviour alone. The ablation configurations quantify this.
6. Findings are specific to industrial human–robot collaboration recorded on Meta
   Aria glasses and should not be assumed to transfer to other tasks or hardware.
7. Four data-quality issues documented in `gazeload-eda.md` are not corrected in this
   pipeline: an artifact population in the saccade features, invalid gaze vectors,
   the retention of Participant 07, and the exact redundancy between `SaccRate` and
   `saccade_count`. See `results.md` §4 for magnitudes and consequences. All four
   reduce measured performance rather than inflating it.
